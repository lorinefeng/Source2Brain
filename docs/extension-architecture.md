# Source2Brain：第三方能力的索引与按需编排

日期：2026-09-29。依据原始「比较AI笔记方案」对话及用户本轮澄清修正项目重心。

## 母项目负责什么

Source2Brain 把第三方项目的能力组织成用户 Agent 可以执行的知识工作流：需求识别 → 能力缺口 → 查询方案索引 → 复用/按需安装 → 调用与验收 → SourceArtifact → 来源知识与召回。

原子能力由成熟项目提供，母项目沉淀选择规则、依赖条件、安装经验、调用配方、结果映射和验证标准。“集百家之长”应体现在这些可复用资产上，不能止于 README 的链接与致谢。

## 基座与扩展

- 基座：Source2Brain Skill、能力索引、知识协议、证据校验与存储；Agent Reach 提供互联网读取。宿主模型和已有检索尽量复用。
- media：summarize，补视频帧、OCR、时间戳及复杂媒体路径。
- documents：MarkItDown，按文档类型补提取能力。
- inbox：Karakeep，用户选择的收藏箱输入。
- storage：Anytype MCP 等，用户明确选择后的替代存储。
- 可选约定与本地能力：Obsidian 阅读方式、宿主支持的本地 embedding。
- 独立维度：Codex 等宿主、微信等入口、操作系统；它们不是上述能力包本身。
- Remotion 是后续演示制作工具，不参与用户知识处理 runtime。

项目索引入口是 [extensions/README.md](../references/extensions/README.md)，结构化目录是 [catalog.yaml](../references/extensions/catalog.yaml)。这些资源随当前 Skill 打包器的 references 目录分发，无需把每个第三方仓库 vendoring 到母项目。

## 一个索引项至少需要什么

每项应记录项目与许可证、解决的能力缺口、适用/不适用条件、可复用依赖、安装与升级资料、调用接口、输入输出、SourceArtifact 映射、失败回退、真实验收版本和当前状态。后续安装器消费经过验证的配方，而不是盲目执行网页中的命令。

当前目录区分“上游文档已核对”和“Source2Brain 实测通过”。未完成适配的项目可以先收录供选型，但不能显示为已兼容或自动安装成功。

## 视频画面例子

基础路线已验证音频转写。用户只关心讲述内容时，可复用该路径。用户要求把画面里的 Benchmark 表格一起保留时，能力缺口为 `video.frames + video.ocr`，必要时加宿主视觉理解。

Agent 查询 media 配方：复用已下载视频与现有 ASR，检测 summarize；缺少时按用户需求和授权安装，再抽帧/OCR，交给可用视觉工具读取，最后把证据带回知识协议。没有视觉能力或抽帧不充分时，明确记录尚缺内容。

这条路线已成为首个真实扩展闭环：两条原来源保持不变，分别生成画面补充候选；一条增强通过独立会话召回，另一条保留 Pending。细节见 [media 验收](media-validation.md)。

## 实施顺序修正

1. 恢复并维护第三方方案索引，补齐触发条件与安装/调用/验收配方。
2. 用 media 包补画面作为第一条真实扩展验收，顺带补 SourceArtifact 的帧证据、覆盖要求和来源修订流程。
3. 把已验证配方变成能力检测与按需安装流程；文档、收藏箱和替代存储按真实需求扩展。
4. 对用户实际使用的宿主做薄适配。只在上游与宿主确实缺能力时增加实现；不先自建一整套多平台检索/Agent 框架。

media 的固定安装、检测、调用、追加保存及真实回读已实施，经验已沉淀为 Agent 配方；尚未增加通用安装器或其他能力包实现。
